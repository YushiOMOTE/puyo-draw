# Tokopuyo Tsumo Search Specification

This document defines the Tokopuyo Search Tsumo dialog and its static search index. It supplements `docs/SPECIFICATION.md` and `docs/TOCOPUYO_TSUMO_SPECIFICATION.md`.

## Purpose and scope

Search Tsumo lets a user choose one of the `65,536` predefined Tokopuyo patterns for the current session. It is a session control, not a persistent library, sharing feature, or custom queue editor.

The search covers the deterministic patterns generated by `tokopuyo/queue.js`. Pattern number `No. N` corresponds to seed `N - 1`, so valid numbers are `1` through `65,536`.

## Dialog behavior

- Tokopuyo mode adds a temporary Search Tsumo button directly below Reset in the left rail. The button may use a placeholder icon until the final icon is selected.
- Pressing the button opens a modal dialog. The dialog has a text input, a candidate list, a confirmation button, and a close button in the upper-right corner.
- The dialog card may scroll on narrow screens. Backdrop click and Escape close the dialog.
- Opening or closing the dialog does not mutate the session. Search state is discarded when the dialog closes.
- The confirmation button is disabled until a candidate is selected.
- Selecting a candidate highlights the complete candidate row and enables confirmation. Confirming starts a fresh empty Tokopuyo session with the selected pattern number.
- Confirmation has the same reset semantics as an ordinary Tokopuyo pattern reset: it clears board state, hand index, Undo/Redo history, score, chain count, review data, step resolution, garbage-mode state, and suggestion caches. The selected pattern's Current is shown immediately after confirmation.
- While the dialog is open, application keyboard shortcuts are inactive. Text input remains usable with normal browser editing behavior.

## Query grammar

The input value is evaluated as follows, in order:

1. The empty value has no candidates.
2. A value matching `^[0-9]+$` is a pattern-number query. Leading zeroes are removed before conversion; an all-zero value is invalid. The normalized number must be between `1` and `65,536`, inclusive. The result is an exact match, never a number-prefix match.
3. A value matching `^[rgbpy]+$` case-insensitively is a color-prefix query. The value is normalized to lowercase and matched against the canonical individual-puyo sequence.
4. Every other value has no candidates. This includes mixed digits and letters, whitespace, punctuation, and letters outside `rgbpy`.

The result is recalculated after every input event. Invalid input simply renders an empty candidate area and does not show an error state.

## Canonical sequence and candidate rendering

Each generated pattern contains 128 pairs. Its canonical individual-puyo sequence is the flattened `hands` sequence in hand order, taking each hand's `axis` puyo followed by its `child` puyo. The searchable sequence therefore contains 256 color symbols. The color-code mapping is:

| Symbol | Color |
|---|---|
| `r` | red |
| `g` | green |
| `b` | blue |
| `y` | yellow |
| `p` | purple |

The candidate row contains:

- the localized pattern number, for example `No. 12344`;
- the first eight individual puyos, rendered left-to-right as eight colored circular elements;
- an accessible text alternative describing the number and colors.

Candidates are always ordered by ascending pattern number and limited to five rows. Numeric exact queries produce zero or one row.

## Search index

### Design

The public build must not synchronously generate and scan all `65,536` patterns for each color-prefix keystroke. A build-time generator creates a static Trie index from the deterministic queue generator.

The Trie indexes the first 6 individual-puyo symbols of every pattern. Each node represents one valid prefix, has zero or more child nodes, and retains a sorted list of the first five pattern numbers in its subtree. Candidate lists retain ascending pattern-number order and are capped at the first five numbers needed by the UI, except for the deepest indexed nodes, which retain every candidate needed for longer-prefix exact comparison.

The index is generated from all patterns, including patterns whose first 6 symbols share a prefix with many other patterns. It must not depend on the currently selected palette, current hand, board contents, or locale.

### Queries up to 6 symbols

For a color-prefix query of length 1 through 6, the runtime walks the Trie one symbol at a time. A missing edge returns no candidates. At the matched node, the runtime returns the already sorted first five pattern numbers.

The Trie must preserve deterministic ordering even when several patterns have the same indexed prefix. No randomization or generation order is permitted in the displayed result.

### Queries longer than 6 symbols

For a color-prefix query longer than 6 symbols, the runtime first walks the first 6 symbols in the Trie. The resulting pattern-number candidates are then checked by exact comparison against the requested full prefix using the canonical generated sequence. Only the narrowed candidates are generated or read for this comparison; the runtime must not scan all patterns. With the current generator, a six-symbol prefix has at most 39 candidates.

If the query is longer than the 256-symbol canonical sequence, it has no match. A valid query may be longer than 6 symbols, but the index itself stores no more than the first 6 symbols.

### Numeric queries

Numeric queries bypass the Trie. After normalization and range validation, the runtime converts `No. N` to seed `N - 1`, generates that one pattern, and renders it as the sole candidate.

## Build-time index generation

The index is a generated public asset and must be reproducible from the checked-in queue generator.

### Required procedure

1. Run the repository's index-generation script from the repository root before a public release.
2. The script must enumerate seeds `0` through `65,535`, call the canonical pattern generator, flatten each pattern into its 256-symbol sequence, and insert the first 6 symbols into the Trie with pattern number `seed + 1`.
3. Serialize the Trie into a static JavaScript module consumed by the application. The generated module stores each TypedArray as Base64 and decodes it to the declared TypedArray when the module is evaluated; this avoids multi-megabyte numeric-literal source while keeping the runtime lookup format simple. Serialization must preserve child ordering and ascending candidate ordering.
4. Run the index verification step. It must confirm that there are exactly `65,536` patterns, every pattern number is in range, every generated sequence has 256 symbols, and every indexed candidate is returned by an independent direct-prefix check.
5. Confirm representative exact-number queries, leading-zero queries, invalid number queries, short color prefixes, 6-symbol prefixes, and prefixes longer than 6 symbols.
6. Run `npm run verify-tsumo-index` and commit the generated asset together with any generator or schema change that affects it. Do not hand-edit the generated index.

The generated asset is `tokopuyo/tsumo-search-index.js`. The generator is `scripts/generate-tokopuyo-tsumo-index.mjs`.

### Regeneration triggers

Regenerate the index whenever any of these change:

- the deterministic pattern-generation algorithm;
- color ordering or color-code mapping;
- the canonical axis/child flattening order;
- the indexed prefix length;
- the serialized Trie format.

The application must fail the verification step rather than silently using an outdated index.

## Verification requirements

Focused tests must cover:

- `No. 1`, `No. 65,536`, leading-zero normalization, `0`, and out-of-range numbers;
- exact-match behavior for numeric input, including the absence of numeric prefix matches;
- case-insensitive `rgbpy` queries;
- rejection of mixed, whitespace-containing, and unsupported strings;
- ascending No. ordering and the five-row limit;
- Trie lookup for prefixes from length 1 through 6;
- exact filtering for prefixes longer than 6;
- no match for a prefix longer than the canonical sequence;
- equivalence between indexed results and independent direct scanning;
- session reset semantics after confirmation and no mutation after cancellation.

UI verification must include a narrow mobile viewport, keyboard input, candidate selection highlighting, disabled/enabled confirmation state, modal scrolling, backdrop close, and Escape close.
